# B2 系统架构与设计文档

> **文档目的**：完整描述YMT OMS V1.0 的技术架构与设计决策，作为后续二次开发、对接、扩展的权威参考。

---

## 一、系统总览

YMT OMS 是一套**前后端分离的 SPA（单页应用）**：

- **前端**：React 18 单页应用，构建为静态资源由 Nginx 直接托管
- **后端**：Express + TypeScript HTTP 服务，由 PM2 守护，监听 `127.0.0.1:3001`
- **数据库**：阿里云 RDS PostgreSQL，通过 Prisma ORM 访问；ECS 使用 RDS 内网地址连接
- **网关**：Nginx 反向代理，将 `/api/*` 转发至后端，其余路径返回前端静态文件

### 1.1 部署拓扑

```
                ┌────────────────────────────────────────┐
                │            阿里云 ECS 主机              │
                │                                          │
   用户浏览器  →  │   Nginx :80/:443                        │
                │     ├── /         → 前端静态资源        │
                │     └── /api/*   → reverse_proxy        │
                │                      ↓                  │
                │                  PM2: Node :3001        │
                └────────────────┬───────────────────────┘
                                 │  阿里云内网
                                 ↓
                       阿里云 RDS PostgreSQL
```

第一阶段交付以该云上架构为准，不规划企业本地化部署。后续如企业明确要求完全内网化，可另立二期迁移方案。

```
├── pages/               角色化页面
│   ├── LoginPage.tsx
│   ├── SalesView.tsx           业务员
│   ├── ProcurementView.tsx     采购
│   ├── ProductionView.tsx      生产
│   ├── LogisticsView.tsx       物流
│   ├── GMView.tsx              审批管理（含发货审批）
│   ├── UserReviewPage.tsx      用户管理
│   ├── Dashboard.tsx           数据看板
│   └── Workbench.tsx           个人工作台
├── components/          通用组件
│   └── ui.tsx                  Card / Section / EmptyHint
├── hooks/               自定义 Hook
└── utils/               工具函数
```

### 4.2 页面路由

App 为**单页 Tab 切换**模式，不使用 React Router。状态保存在 `App.tsx` 的本地 state 中：

```
登录 → /loginPage
通过 → currentTab state
       ├── 工作台      Workbench
       ├── 业务员      SalesView
       ├── 采购        ProcurementView
       ├── 生产        ProductionView
       ├── 物流        LogisticsView
       ├── 审批管理    GMView
       ├── 用户管理    UserReviewPage
       └── 数据看板    Dashboard
```

Tab 可见性由当前用户的角色矩阵决定（见第 8 节权限模型）。

### 4.3 状态管理

- **未引入 Redux / Zustand**：业务复杂度未达需要全局状态管理库的程度
- **本地 state**：每个页面用 `useState` / `useReducer` 管理
- **跨页面共享数据**：通过 localStorage（user / token）与 API 重新拉取
- **Form 状态**：完全交给 AntD `Form` 实例管理（`useForm()` + `setFieldsValue`）

### 4.4 UI 组件库

- **AntD 5 为主**：Table / Form / Modal / Drawer / Select / DatePicker / Switch 等
- **Tailwind CSS 辅助**：原子类调样式（间距、颜色、阴影）
- **全站统一样式约定**：
  - 表格：`tableLayout="fixed"`、无水平滚动、直角无圆角
  - 合同编号字段：全站统一 `.sales-table-code` 类（slate-blue 色、tabular-nums、weight 600）
  - 筛选器：`.ymt-filter-bar` 无下边框
  - 主色：`#4B6B9A`（合同号）/ `#16a34a`（备齐绿）

### 4.5 网络请求层

`api.ts` 集中管理：

- 创建 axios 实例，`baseURL = '/api'`
- 请求拦截器：自动注入 `Authorization: Bearer <token>`
- 响应拦截器：统一错误处理，401 跳转登录
- 导出按业务领域分组的函数（`ordersApi.list()`、`customersApi.create()` 等）
- `getApiErrorMessage()` 工具：从错误响应中解析人类可读的错误信息

### 4.6 权限路由守卫

- `App.tsx` 在登录后读取 `user.role / user.subRole`
- 根据权限矩阵决定**哪些 Tab 可见**
- 每个 Tab 内部页面再做一次细粒度判断（如"内勤跟单"看到"发货审批"按钮，"审批经理"看到"订单审批"按钮）
- 数据级权限通过后端接口过滤实现（前端不可信）

### 5.3 中间件链

请求进入后的处理顺序：

```
1. CORS                  跨域白名单
2. Helmet                安全响应头
3. Morgan                访问日志
4. express.json()        JSON body 解析
5. express.urlencoded()  表单解析
6. (路由特定)
   ├── multer            文件上传（仅 /api/excel）
   ├── authenticate      JWT 鉴权（除登录、注册）
   ├── authorize         角色 / 权限授权
   └── validate          Zod 入参校验
7. 业务处理
8. 统一错误处理（错误抛出 → httpError → JSON 响应）
```

### 5.4 数据访问层（Prisma）

- **单例 Client**：`prisma.ts` 导出唯一实例
- **类型安全**：所有查询自动生成 TS 类型
- **事务**：关键写操作（创建订单 + 订单明细 + 审批日志）使用 `prisma.$transaction`
- **迁移**：`prisma migrate` 管理 schema 演进
- **种子数据**：`prisma/seed.ts` 提供初始管理员账号

### 5.5 业务服务层

业务逻辑沉淀在 `src/lib/`，路由文件只负责"接收请求 → 调用 lib → 返回响应"：

- `contractNumbers.ts`：原子化生成合同编号，含冲突重试
- `dashboardCache.ts`：内存级缓存看板数据，写订单时主动清除
- `excelOrderParser.ts`：Excel 智能解析核心（自主创新点）
- `userPermissions.ts`：集中定义 `canViewOrders / canApproveOrder / canApproveShipment` 等判定函数

### 5.6 错误处理

- `httpError(status, message, code?)`：统一抛错入口
- Express 全局错误中间件：
  - `httpError` → 返回对应 status + JSON
  - `Multer` 文件大小超限 → 413
  - 未知错误 → 500 + 脱敏日志
- 客户端通过 `getApiErrorMessage()` 解析

## 七、工作流引擎设计

### 7.1 订单状态机

订单状态共 **11 个**，状态间通过 **20+ 条迁移规则** 连接：

```
draft  ─submit─→  pending_approval  ─approve─→  procurement
                       │
                       └─reject_modify─→ draft（业务员修改后重新提交）
                       └─reject──────→ rejected（终态）

procurement  ─finish_procurement─→  production

production  ─finish_production─→  ready_ship

ready_ship  ─ship──────────────→  pending_ship_approval

pending_ship_approval
       ├─approve_ship─→  shipped（终态）
       └─reject_ship──→  ready_ship（物流重新提交）
```

### 7.2 状态转换规则

所有规则集中定义在 `orders.ts` 的 `TRANSITIONS` 常量中：

```ts
{
  submit:           { from: 'draft',                 to: 'pending_approval',       perm: canCreateOrder },
  approve:          { from: 'pending_approval',      to: 'procurement',            perm: canApproveOrder },
  reject_modify:    { from: 'pending_approval',      to: 'draft',                  perm: canApproveOrder },
  reject:           { from: 'pending_approval',      to: 'rejected',               perm: canApproveOrder },
  finish_procurement:{from: 'procurement',           to: 'production',             perm: canHandleProcurement },
  finish_production:{ from: 'production',            to: 'ready_ship',             perm: canHandleProduction },
  ship:             { from: 'ready_ship',            to: 'pending_ship_approval',  perm: canHandleLogistics },
  approve_ship:     { from: 'pending_ship_approval', to: 'shipped',                perm: canApproveShipment },
  reject_ship:      { from: 'pending_ship_approval', to: 'ready_ship',             perm: canApproveShipment },
}
```

每次迁移自动执行 3 件事：

1. 校验 from 状态匹配
2. 校验调用者权限
3. 写入 `ApprovalLog`（操作人、原状态、新状态、原因、时间戳）

### 7.3 审批日志记录

`ApprovalLog` 全留痕，字段：

- `orderId`：订单 ID
- `action`：动作（submit / approve / reject / ship / ...）
- `fromStage` / `toStage`：状态变化
- `operator`：操作人姓名
- `reason`：可选原因（驳回、退回时必填）
- `createdAt`：时间戳

任何审计、客户投诉、内部追责均可基于 `ApprovalLog` 查到完整证据链。

## 八、权限模型

### 8.1 角色定义

`User.role` 枚举：

| 角色 | 中文 | 主要业务 |
|---|---|---|
| `sales` | 业务员 | 订单与客户 |
| `purchasing` | 采购 | 物料与库存 |
| `production` | 生产 | 生产任务 |
| `logistics` | 物流 | 发货 |
| `manager` | 经理 | 见子角色 |
| `admin` | 系统超级管理员 | 全部权限（极少授予） |

### 8.2 经理子角色

`User.subRole` 枚举（仅 `role = manager` 时有效）：

| 子角色 | 中文 | 主要权限 |
|---|---|---|
| `approval_manager` | 审批经理 | 订单审批（通过 / 退回 / 驳回） |
| `clerk` | 内勤跟单 | 发货审批、只读用户列表 |
| `system_admin` | 系统管理员 | 用户管理 + 全部审批权 |

### 8.3 权限判定（`userPermissions.ts`）

集中定义判定函数，避免散落各处：

```ts
canViewOrders(user)           // 业务员看自己 / 其他角色看相关
canCreateOrder(user)          // sales / manager / admin
canApproveOrder(user)         // manager.approval_manager / system_admin / admin
canHandleProcurement(user)    // purchasing / admin
canHandleProduction(user)     // production / admin
canHandleLogistics(user)      // logistics / admin
canApproveShipment(user)      // manager.clerk / manager.system_admin / admin
canManageUsers(user)          // manager.system_admin / admin
canCreateOrderForSales(...)   // 用于"经理代下单"场景
```

### 8.4 三层授权防御

1. **前端路由层**：决定 Tab 与按钮可见性（用户体验，不可信）
2. **后端中间件层**：`requirePermission(canXxx)` 在路由入口拦截
3. **后端数据层**：在查询条件中加入 `where: { salespersonId: user.id }` 等过滤（防止越权读取）

## 九、缓存与性能

### 9.1 仪表盘缓存策略

- 看板 KPI / 月度趋势 / 客户分布 等聚合查询代价较高
- 使用内存级缓存：`dashboardCache.ts`
  - 首次请求 → 查库 → 缓存（带 TTL）
  - 后续命中 → 直接返回
- **写订单时主动失效**：`clearDashboardCache()` 在订单创建 / 状态变更后调用

### 9.2 查询优化

- 高频查询字段建索引（合同号、状态、业务员、客户名）
- 列表接口分页（默认 20 / 页）
- 关联查询使用 `include` 而非 N+1 循环
- 大表统计使用 `groupBy` + 数据库聚合

## 十、日志与监控

### 10.1 应用日志

- **PM2 日志**：标准输出 / 错误流，按天切割
- **Morgan**：HTTP 访问日志，记录 IP / 路径 / 状态码 / 耗时
- **业务日志**：关键操作（登录、订单创建、审批、改密）通过 `console.info` 输出，可由 PM2 集中收集

### 10.2 错误监控

- 后端全局未捕获异常 → 写入 PM2 error 流
- 前端 axios 拦截器 → 错误统一弹出 `message.error`
- 可选接入：Sentry / 阿里云 ARMS（预留扩展点）

### 10.3 访问监控

- Nginx access log → 流量、状态码分布
- PM2 metrics → CPU / 内存 / 响应时间
- 数据库 → 阿里云 RDS 慢查询、连接数、存储空间和备份任务面板

## 十一、安全设计

> 完整安全审计参见 **B4 安全审计报告**。

| 维度 | 措施 |
|---|---|
| 身份认证 | PBKDF2-SHA512（10 万次迭代），盐值随机 |
| 会话 | JWT，24 小时有效期，载荷含 tokenVersion |
| Token 失效 | 用户禁用 / 改密时递增 tokenVersion，旧 token 立即失效 |
| 入参校验 | Zod schema 强类型校验，类型不符直接 400 |
| SQL 注入 | Prisma 参数化查询，杜绝拼接 |
| XSS | React 默认转义；后端响应 JSON，无 HTML 模板 |
| CSRF | 无 cookie 会话，token 通过 Authorization 头传输 |
| 文件上传 | 类型 + 大小 + 签名（魔数）三重校验 |
| 跨域 | CORS 白名单 |
| 响应头 | Helmet（X-Frame-Options / X-Content-Type-Options / HSTS） |
| 审计 | ApprovalLog 全留痕 |
| 数据库静态加密 | RDS 云盘加密保护磁盘和快照，不影响业务查询 |
| 备份恢复 | RDS 自动备份 + 企业经理电脑 7 天冷备份 + SHA256 校验 |
